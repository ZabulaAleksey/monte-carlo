# Канонический контекст проекта

Этот файл хранит требования, которым нужно давать наивысший приоритет при
продолжении чата или после сжатия контекста. Диагностические сообщения и
разовые ошибки сюда не переносятся. Новые сообщения пользователя с заголовком
`Этап` следует добавлять в этот документ.

## Общие правила

- Рабочая папка проекта: `monte-carlo`.
- Перед каждым этапом изучать существующий проект и архитектуру.
- Не переписывать рабочие части без необходимости и не удалять функциональность.
- Соблюдать SOLID, разделение ответственности и строгую типизацию.
- Не помещать бизнес-логику в API-контроллеры и React-компоненты.
- Добавлять обработку ошибок, структурированное журналирование и автотесты.
- После изменений запускать тесты, линтер и сборку, обновлять README.
- Не переходить к следующему этапу самостоятельно.
- В отчёте перечислять созданные и изменённые файлы, архитектурные решения,
  команды запуска и проверки, а также оставшиеся ограничения.
- Предпочтительный стек: Next.js, React, TypeScript; Python, FastAPI, Pydantic;
  NumPy, Pandas, SciPy, Numba; PostgreSQL, Alembic, SQLAlchemy 2; TradingView
  Lightweight Charts и ECharts; MQL5 через HTTP или WebSocket; pytest, Vitest,
  React Testing Library; Docker Compose.

## Этап 1. MVP и базовая архитектура

- Структура: `apps/frontend`, `apps/backend`, `infra`, `docs`.
- Frontend: Next.js, React, строгий TypeScript, базовая навигация и страницы
  Dashboard, Market Data, Trades, Strategies, Settings. API-клиент отделён от
  компонентов, конфигурация через environment variables.
- Backend: FastAPI со слоями `api`, `application`, `domain`, `infrastructure`;
  `GET /health`, `GET /api/v1/info`; централизованные ошибки, структурированное
  логирование, Pydantic Settings.
- PostgreSQL, SQLAlchemy 2 и Alembic: модели и миграции `symbols`, `candles`,
  `accounts`, `trades`.
- Свеча: `id`, `symbol_id`, `timeframe`, `open_time`, `open`, `high`, `low`,
  `close`, `volume`.
- Сделка: `id`, `account_id`, `symbol_id`, `external_id`, `side`, `volume`,
  `open_price`, `close_price`, `opened_at`, `closed_at`, `profit`, `commission`,
  `swap`, `status`.
- Docker Compose для frontend, backend и PostgreSQL; `.env.example` без секретов.
- Demo-данные для проверки без MetaTrader.
- Тесты: `/health`, CRUD символов, сохранение свечей и сделок, загрузка frontend.
- Критерий готовности: запуск через Docker Compose, frontend читает backend,
  PostgreSQL хранит символы, свечи и сделки.
- Не реализовывать стратегии, бэктестинг, Монте-Карло и генетический алгоритм.
- Результат этапа публикуется коммитом `Этап 1. MVP и базовая архитектура`.

## Этап 2. Мост с MetaTrader 5

- Продолжать существующий проект и реализовать безопасный односторонний мост
  между MetaTrader 5 и FastAPI.
- Backend принимает heartbeat, сведения о счёте и символах, свечи, открытые
  позиции и историю сделок.
- Ориентировочные endpoints: `POST /api/v1/mt5/heartbeat`, `/account`, `/symbols`,
  `/candles/batch`, `/positions`, `/trades/batch` и endpoint статуса терминала.
- Отдельный API-ключ только из environment variable; не выводить секреты в логи.
- Идемпотентное пакетное сохранение без дублей свечей и сделок.
- Валидировать время, цены, объёмы и направление; журналировать ошибки
  синхронизации; хранить последний heartbeat.
- MQL5 EA или сервисный скрипт отправляет heartbeat, счёт, новые свечи и сделки,
  повторяет временно неуспешные запросы и никогда не открывает реальные сделки.
- Frontend показывает состояние MetaTrader, последнюю синхронизацию, последние
  свечи и сделки, а также предупреждение об устаревшем соединении.
- Добавить API-тесты и тесты идемпотентности.
- Не реализовывать отправку торговых приказов из backend в MetaTrader.
- `BridgeBaseUrl`, `BridgeTerminalId`, `MT5_API_KEY` должны присутствовать в
  `.env.example`, `mt5/config.example` и input-параметрах MQL5. В инструкциях
  всегда указывать точный путь к редактируемому файлу.
- При online/cached MT5 frontend не смешивает реальные данные с Demo: demo-свечи
  и demo-сделки скрываются, источник данных явно обозначается.
- Market Pulse показывает зелёные бычьи и красные медвежьи японские свечи.
  Выбранные символ и таймфрейм сохраняются в `localStorage`.
- Результаты этапа публикуются коммитами `Этап 2. Мост с MetaTrader 5` только по
  явному запросу пользователя.

## Будущие этапы 3–13

Этапы ниже описывают целевое развитие проекта, а не уже реализованную
архитектуру. Фактическое текущее состояние отражено в
[`architecture.md`](architecture.md). Каждый следующий этап начинается только
по явному запросу пользователя, расширяет существующую реализацию и сохраняет
контракты завершённых этапов. Поэтапные промпты находятся в
[`../prompts/`](../prompts/README.md).

Целевой поток данных:

```text
MT5
 ↓
PostgreSQL / опционально TimescaleDB
 ↓
Arrow / Parquet / DuckDB
 ↓
ComputeEngine / ComputeBackend
 ↓
Strategy / Backtest / Monte Carlo / Genetic
 ↓
Reports
 ↓
REST / WebSocket / UI
```

Сквозные компоненты будущих этапов:

- RabbitMQ для очередей тяжёлых задач;
- Redis только для кэша или краткоживущего состояния, когда это оправдано;
- Temporal для длительных и восстанавливаемых многошаговых процессов;
- OpenTelemetry для связанных метрик, журналов и трассировок;
- детерминированная CPU-реализация как эталон до добавления ускорителей.

### Этап 3. Схема рыночных данных

- Расширить существующую схему PostgreSQL и миграции, не создавая параллельную
  модель данных.
- Добавить TimescaleDB-совместимую структуру для тиков, свечей и рыночных
  событий. Подключение самого расширения TimescaleDB требует отдельного
  архитектурного решения.
- Хранить точность, часовой пояс, источник и происхождение данных явно.
- Определить миграции, индексы и политику хранения.
- Исключить утечку будущих данных в аналитических запросах.

### Этап 4. Расширение FastAPI API

- Развивать существующие границы `application`, `domain` и `infrastructure`, не
  создавать второй API-каркас.
- Добавить типизированные API рыночных данных, стратегий, заданий и результатов.
- Добавить пагинацию, фильтрацию, идемпотентность мутаций и заданий,
  структурированные ошибки.

### Этап 5. Развитие интерфейса терминала

- Расширить существующий frontend представлениями dashboard, рынка, стратегий,
  результатов и заданий.
- Сохранить явное разделение demo, cached и online-данных.
- Использовать WebSocket или событийные обновления только при обоснованной
  необходимости.
- Не помещать бизнес-логику в React-компоненты.

### Этап 6. Стратегии и эталонный CPU-бэктест

- Реализовать независимый от FastAPI и MT5-адаптеров доменный движок.
- Гарантировать детерминизм набора данных, версии алгоритма и seed.
- Исключить look-ahead, учитывать комиссию и проскальзывание.
- Обеспечить воспроизводимые результаты и исходный benchmark до ускорения.

### Этап 7. Эталонный Monte Carlo на CPU

Поддерживаемые варианты:

- перестановка порядка сделок;
- bootstrap/resampling;
- изменение проскальзывания и комиссии;
- возмущение параметров;
- моделирование пропущенных сигналов;
- распределения просадки и риска разорения.

Каждый запуск хранит детерминированный seed, формирует распределения и
доверительные показатели и проходит benchmark для 10 тысяч, 100 тысяч и
1 миллиона сценариев. Методические требования описаны в
[`monte-carlo-methods.md`](monte-carlo-methods.md).

### Этап 8. Генетическая оптимизация и отчёты

Целевой конвейер:

`GA-кандидат → обычный бэктест → Monte Carlo robustness → Robust Fitness → следующее поколение`.

- Задать границы параметров и воспроизводимые population/generation.
- Оценивать robust fitness, а не только лучший исторический P&L.
- Выводить предупреждения о переобучении.
- Сохранять эксперименты и отчёты с полным происхождением данных.

### Этап 9. RabbitMQ и Celery workers

- FastAPI ставит тяжёлые задания в очередь и не выполняет их синхронно.
- RabbitMQ используется как broker для импорта, бэктестов, Monte Carlo,
  оптимизации и отчётов.
- Задания поддерживают retry, идемпотентность, timeout, cancel, status и
  progress.
- Redis остаётся опциональным кэшем/хранилищем состояния и не подменяет broker.

### Этап 9.6. Temporal orchestration (опционально)

Temporal добавляется после этапа 9 только для длительных многошаговых процессов,
например `import → validate → backtest → Monte Carlo → optimize → report`.
Temporal отвечает за orchestration и восстановление, а RabbitMQ/Celery — за
исполнение задач, где это уместно. Разделение ролей описано в
[`observability-and-workflows.md`](observability-and-workflows.md).

### Этап 10. Arrow, Parquet и DuckDB

- Использовать Arrow как формат обмена в памяти, Parquet для аналитических
  наборов и результатов, DuckDB для локальных аналитических запросов.
- Снижать число копирований и сериализаций.
- Адресовать наборы данных по версии, hash и provenance.

### Этап 10.5. Hardware Abstraction Layer

Ввести единый контракт `ComputeBackend` для CPU/NumPy, Numba,
multiprocessing, CUDA, OpenCL и опциональных WebGPU, Vulkan Compute и WASM.
Выбор backend: `auto | cpu | cuda | opencl | webgpu | vulkan | wasm`.
Каждый ускоритель требует fallback, тестов эквивалентности и полного benchmark.
Подробнее: [`compute-backends.md`](compute-backends.md).

### Этап 11. ComputeBackend auto/cpu/cuda/opencl

- Определять возможности среды выполнения до выбора backend.
- Сохранять единые алгоритмические контракты и CPU-эталон.
- Проверять эквивалентность с явно заданными допусками.
- Выполнять безопасный fallback.
- Записывать backend, устройство и версии в provenance результата.

### Этап 12. Профилирование и CUDA Graphs

Этап выполняется только после измерений, подтвердивших существенные накладные
расходы запуска или оркестрации GPU. Нужно профилировать kernels и передачу
данных, сохранить обычные CUDA/OpenCL/CPU-пути и измерять end-to-end wall-clock
ускорение, а не только время kernel.

### Этап 13. Realtime, AI и экспериментальные адаптеры

Только после отдельного согласования могут добавляться WebTransport/HTTP3,
изолированный LLM-помощник для стратегий и MQL5, заметки по TEE/confidential
compute, а также WebGPU/Vulkan/WASM-эксперименты. Любая такая возможность
остаётся за feature flag, имеет fallback, тесты и benchmark.

- Для этапов производительности приложить воспроизводимый benchmark.
- Обновить README и релевантную проектную документацию в соответствии с
  фактическим состоянием реализации.
- Не переходить к следующему этапу автоматически.
- Выполнять merge только после проверки и явного разрешения пользователя.
